# UI polish audit — 4 November 2026

Reviewed the current checkout in the browser at `http://127.0.0.1:5173`, using the existing fixture runtime and the superadmin account. Desktop review used 1280×800 and 1440×900 layouts; the narrow-screen pass used a 390×844 CSS viewport. No application code or real database records were changed.

The green palette, navigation icons, rounded controls, and typography already give the portal a consistent identity. The greatest gains will come from fixing layout constraints, making actions accurately describe their behavior, and simplifying dense forms.

## Fix first

1. **Make the authenticated layout responsive.** The shared `.content` retains `min-width: 800px`. At a 390px viewport, Dashboard, Locations, Users, Profile, and Map Editor measured 800px document width; Logs also overflowed. Headers and filters run off-screen, and map tools/inspectors become difficult to reach. Remove the shared minimum, stack filters and actions, and contain horizontal scrolling inside tables. On phones, map inspectors should become a bottom sheet or a separate panel. This affects substantially more than table responsiveness. Owner: `frontend/admin/src/styles.css`, especially `.content`.
2. **Resolve the prototype behavior on My Profile.** The current route directly renders `AccountPrototypeDialog` and `BackupPrototype`. Profile edits only update page memory, while the dialog offers an ordinary “Save Changes” action. Backup history and schedule controls are simulated. Use the existing persistent profile/backup implementations for the normal route, or clearly label the entire experience as a preview before users act. The floating variant switcher is development-only, but the prototype components themselves are not similarly gated in `Profile.tsx`. This is a source-confirmed behavior issue, not a claim about a deployed build. Owners: `frontend/admin/src/features/profile/Profile.tsx`, `BackupRecovery.tsx`, and the prototype directories.
3. **Give dashboard totals proper room.** The metric cards are fixed at 196px high, with a 56px gap above their labels. DOM measurements put the total text about 8px beyond the card's bottom. Depending on the rendered layout, the numbers look clipped or pressed against the rounded edge. Use a normal vertical layout with sufficient bottom padding, and reduce the gap between icon and value. Owner: `.metric-grid` rules in `styles.css`.

## Recommended sequence

First fix the shared responsive shell and profile/backup truthfulness. Then fix metric card sizing, location dialog copy/order, repeated floor choices, and the map's initial validation message. Finish with filter alignment, compact timestamps, button target sizes, and secondary visual refinements.

Keep the current color system and overall branding. A redesign is unnecessary to address these findings.

## Coverage and limits

Visited every primary routed screen: Login, Forgot Password, Forgot Username, Dashboard, Map Editor, Locations, Users, Profile, and the not-found screen. Inspected Dashboard Overview/Analytics; both user-directory tabs; location hierarchy and action menu; add/edit location dialogs; add-administrator dialog/menu; log details; profile-edit, change-password, and backup-schedule dialogs; map loading, issues, legend, building inspector, Route Node, Building Polygon, and Pathway menu states. Reached password recovery's code and new-password steps with the fixture.

This was a visual/interaction audit, not an exhaustive functional test. No destructive confirmations, password changes, restores, or real email deliveries were performed. The username-result and password-reset-success screens were not reached, and every map editing subflow/error state was not exercised. The alternate backup variants B/C were not reviewed. Some preview clicks timed out; a fallback browser was unavailable, and keyboard interaction allowed the password recovery inspection to continue. Those tool failures are not listed as application defects. Contrast ratios, full keyboard navigation, and real-backend behavior remain unverified.
