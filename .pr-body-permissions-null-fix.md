## 1. Superadmin creation and promotion — the merge blocker

A JSON column has **two different nothings**, and the one the schema means by "no permissions recorded" is SQL NULL.

`Admin.permissions` used `JSONB()` with the default `none_as_null=False`, so assigning Python `None` stored the JSON scalar `null` — a *value* — and the migration's shape constraint rejects it, because `jsonb_typeof('null')` is `'null'`, not `'object'`. Creating a superadmin and promoting an administrator both assign `None` deliberately, so both failed with SQLSTATE 23514.

The fix is `none_as_null=True` on the PostgreSQL and SQLite variants alike. **The migration's constraint is untouched** — it was right; the storage was wrong.

I reproduced it first to be sure of the diagnosis:

```
none_as_null on the column type: False
bind_processor(None) -> 'null'
creating a superadmin with permissions=None
  -> IntegrityError: (psycopg2.errors.CheckViolation) new row for relation
     "admin" violates check constraint "admin_permissions_shape"
```

…and after the fix, `bind_processor(None) -> None`, which is SQL NULL.

### The regression coverage

`app/tests/admin_permissions_storage.py` (10 tests) exists because **every SQLite and fake-store test passed through this bug** — neither carried the constraint the migration adds. It puts the constraint back:

- against a **disposable PostgreSQL** when `ISU_TEST_DATABASE_URL` names one, applying the **real migration file** verbatim;
- otherwise against **SQLite with the same rule** written in SQLite's own JSON functions, so an ordinary `pytest` run catches the regression too (as a trigger, since SQLite cannot add a constraint to an existing table).

Two details that make these tests worth having:

- **The assertions ask SQL, not the ORM.** Both nothings deserialize to Python `None`, so `row.permissions is None` passes either way — that is exactly the blind spot that let this ship. They assert `permissions IS NULL` in SQL.
- **One test checks the constraint is actually armed**, so the others cannot pass by simply not being checked.

Reverting the one-line fix turns all 10 red; that is the check I actually care about here.

## 2. Supplied null bypassing validation

`"permissions": null` was read as if the field were absent on create and demotion, and quietly took the view-only default.

**Absent and null are different things.** Leaving the field out takes the default (all four off); sending `null` is a value the caller chose, and the only shape a supplied value may take is the four booleans — so it is refused like any other wrong shape, 400 with `fields.permissions`.

A supplied value is still **ignored for a superadmin target, `null` included**, which is the documented behaviour the issue asked to preserve: a client may hold one form for both roles, and a field that cannot apply must not fail the request. `PUT /api/admins/:id/permissions` already refused null; the create and demote paths now agree with it.

8 new tests in `app/tests/admins.py` cover explicit null on create, on demotion and on promotion, the superadmin exemption, that omission still defaults, and that every wrong shape — null among them — is refused identically so a client cannot tell which kind of wrong it was. Reverting that fix turns 3 of them red.
