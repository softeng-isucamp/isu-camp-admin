Forgot Password and Forgot Username answered **every** well-formed address identically — *"If an account exists for this email, a code has been sent."* An administrator who mistyped their own address was told nothing was wrong and sat waiting for a code that was never sent. The only way out was to guess that the typo was the problem.

`POST /api/recovery/request` now looks the address up against `gmail` and `alternative_email` across all accounts and refuses it unless it resolves to exactly one **active** account:

```
400  {"success": false, "code": "email_not_found",
      "message": "That email is not registered to an administrator account. Check the address and try again."}
```

On success the copy stops hedging too: **"A verification code has been sent to this email."**

## Read this before approving

> **This answer confirms which addresses are administrator accounts.** Anyone can submit addresses one at a time and learn which ones exist. The generic reply existed precisely to prevent that, and this PR gives it up.
>
> It is a deliberate trade for telling an administrator that they mistyped their own address. What remains of the brake is the **per-client cap of 10 requests a minute per IP** and the **60-second resend cooldown** per client and address — enough to make enumeration slow, not enough to make it impossible.
>
> **If that property is wanted back, the thing to remove is this refusal.** It is one branch in `recovery_request`, plus the copy. Nothing else in the feature depends on it.

## One code for three refusals

No account holds the address, the account holding it is **deactivated**, or **two accounts hold it between them** — all three answer `email_not_found` with the same message. The differences are about an account the sender may have no business knowing exists, and an administrator reading the message can act on none of them: the fix for all three is the same conversation with whoever manages accounts.

**Nothing is counted and nothing is stored before the refusal.** A mistyped address spends none of the account's three-per-window request budget and leaves no code entry behind — so a typo cannot cost an administrator a request they will need, and typing invented addresses cannot grow the code store. A test pins the ordering: an unregistered address is refused *before* any restriction is consulted.

**Verification is unchanged and does not depend on any of this.** `verify` and `reset-password` still require the account the code was issued for, so a code never reaches an account the address does not belong to. Guesses at an address with no code still answer `invalid_code` and still count down — the refusal is on the request step only.

## Two cleanups that came with it

### The legacy username-keyed reset routes are gone

`/api/reset/request`, `/api/reset/verify` and `/api/reset-password` keyed codes **by username**, answered an unknown one with `404 "Admin account not found"` — naming which accounts exist, the very thing the generic reply was protecting — and never consulted `alternative_email`. They shared `reset_otps` with the recovery flow through a second key shape, with `legacy_reset_lock` ordered against `recovery_lock` to keep the two from colliding.

All of it is removed: the routes, the lock, the username keys, and `legacy_reset_code_verdict`. A test asserts all three paths now answer **Flask's own 404**, not a JSON refusal from a route that still exists, and that every key left in `reset_otps` is a `(purpose, email)` tuple. Dropping the mixed key shapes also simplifies eviction in `store_recovery_entry`, which no longer has to filter out keys of the other kind to count the pool.

The frontend had already moved: `/reset-password` has redirected to `/forgot-password` since the email-based flow landed (`ffb6f1b`), and that redirect and its test are untouched.

### User Management's password-reset send now issues a code the colleague can use

`send_password_reset_otp` wrote to the **legacy** store under the colleague's username. Nothing redeemed username-keyed codes any more, so the colleague received a code with nowhere to type it — and if they went to the forgot-password page anyway, a *second, different* code was waiting there. Two codes, one inbox, and the one the dialog reported as sent was the one that did not work.

It now issues through the same store, key and budget as a request the colleague would have made themselves: they enter their own address on the forgot-password page and redeem it like any other reset, and it comes out of **that account's** three-per-window budget, so sending from User Management cannot hand out more codes than the colleague could have asked for.

It is refused with `409` when the account's address is one recovery could not resolve — shared with another account, or absent — because a code for such an address could not be redeemed on that page. Refusing here keeps the promise that a code this route reports as sent is a code that works. The audit entry is written only once a code is actually on its way.
