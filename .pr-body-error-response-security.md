Closes #138.

Several backend endpoints answered a 500 with the exception itself, and three backup job messages carried one into the portal's Backup and Recovery interface. The admin frontend hides a 5xx `message` and truncates a failed job message — but that is the frontend. **The response goes out as sent to developer tools and to every other client.** So the detail moves to where it is actually useful: the log, with its traceback, read by whoever can fix the cause.

Nothing in it was ever actionable for an administrator. Driver and ORM text names tables, columns, constraints and the connection; an `OSError` from a client tool names paths on the server.

The locations listings are the two that leaked through `message` rather than `error`, so they are the two whose `message` value changes. Both already logged the detail as a warning before returning it; now they only log it.

## One place decides what a crash may say

`app/routes/route_node.py` had the same five-line handler fifteen times. It is now one helper:

```python
def _failed(message):
    logger.exception(message)
    return _error(message, 500)
```

`_error` was already the shape every refusal in that file uses, so the body is unchanged apart from the dropped key. One site — the convert-point handler — was returning a 500 without logging anything at all; it goes through `_failed` too, so every crash in the file is now recorded.

**`ValidationError` still answers 400 with `str(error)`, deliberately.** Those seven sites are our own validation text, written for the administrator ("latitude must be between -90 and 90"), and they are the useful half of this API's error reporting. Only the unexpected-failure paths were leaking.

## The `error` key is gone, and the contract is not

`"error"` is removed from every response body. **Nothing read it** — `frontend/admin/src/services/api.ts` only ever destructures `message` (and `code`, `fields`, `relationships`). No new fields are added, and no `message` value a client matches on changed: `"Login failed"` is byte-identical, so the client-side fallback at `api.ts:1079` behaves exactly as before.

## Exceptions now reach the log

`services/auth.py` and `services/database.py` were reporting these with `print(...)`, which bypasses logging entirely — so the leaked `error` field was in practice the *only* place the exception was recorded in a deployment that captures logs rather than stdout. Removing the field without fixing that would have lost the detail instead of relocating it.

So both files use `logger.exception` now, which also writes the traceback. `database.py` uses `app.logger`, matching the global `handle_unexpected_error` directly above it; `auth.py` and `route_node.py` gained a module logger. While in `auth.py` I converted its two remaining `print`s — the background recovery mailer and `recovery_failure` — so there is one way exceptions are recorded in that file rather than two.

## Tests

**1041 backend tests pass** (1037 before).

Four regressions added, each asserting *both* halves — that the detail is in the log, and that it is absent from what the client receives:

- a walking-network write whose commit fails (`route_node.py`)

Two existing tests in `app/tests/location.py` asserted the raw `ValueError` text in the response body. `test_invalid_floor_relationship_is_reported_instead_of_projected` is the interesting one: its point is that a bad Floor relationship must not be silently rendered as a valid row, and that still holds — the reporting channel is now the log, so it asserts the detail reaches `caplog` and the body stays safe. These two are the only behavior changes a reader should check against the issue.

## Deliberately left alone

**`backup_jobs.py:601` still sends the client tool's last stderr line as the job message.** The issue listed lines 549, 569 and 589, and the code documents this one as a decision: the tool's own last line says far more than a generic failure, and the password was passed in the environment rather than on the command line, so it is not in there.

Two things worth a separate decision, though:

- it is still raw backend text reaching the portal — `pg_restore: error: could not execute query: relation "building_photo" already exists` describes the schema
- it interacts badly with the frontend's truncate-after-the-colon rule. `pg_dump: error: connection to server failed` renders as **`pg_dump`**, which helps nobody. A colon-free safe sentence is what that rule expects, which is what the three fixed messages above now are.

Reverting a documented decision seemed like the wrong thing to fold into this PR. Happy to change it here if you'd rather.

**`services/check_db.py:77` keeps the driver's first line.** It is the `dev.ps1` / `dev.sh` preflight: it prints to the developer's own stderr and never answers a request.
