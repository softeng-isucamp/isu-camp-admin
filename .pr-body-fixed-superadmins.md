## The hole this closes

"The four superadmins" was a convention. `public.admin.role` was an ordinary column and `PUT /api/admins/:id/role` let anybody holding the role grant it to anybody else — so one promotion, by accident, by a stolen session or by a direct `UPDATE`, made it five, with a fifth account holding Backup & Recovery and everybody else's account.

The set now lives in `public.superadmin_designation`, and the database keeps it.

## One decision to confirm before merge

The issue asks to confirm **whether protection also forbids portal deactivation and deletion of the four**. This implements the proposed policy as the acceptance criteria describe it:

- a designated account's status is refused in **both** directions, and
- delete stays gone for every account (405), which is the stronger form — nothing can address a delete at one of the four however it is phrased.

Deactivation is still possible through the documented operator containment procedure, which is exactly why the database cap counts **designations, not active accounts**: a rule demanding four *active* accounts would make containment impossible. If the decision lands differently, the status refusal is one check in one route.

The four live identities are **not** verified here and appear nowhere in source. They are operator inputs to the migration. **Agree the transfer approvers and the emergency containment path before deploying this.**

## What the database enforces

`migrations/20261107_fixed_superadmins.sql`, one transaction, holding against direct SQL and not only against the API:

| Rule | How |
| --- | --- |
| A designated account holds the superadmin role, and an account without a designation cannot acquire it | `assert_superadmin_designation`, a `DEFERRABLE INITIALLY DEFERRED` constraint trigger on **both** tables, checked at COMMIT |
| At most four designations, ever | the same trigger |
| A designated `public.admin` row cannot be deleted | `guard_designated_admin_delete`, plus `references public.admin(id) on delete restrict` |
| `public.superadmin_designation` cannot be inserted, changed or deleted at all | `guard_superadmin_designation_write` |

**Deferred is load-bearing, not a convenience.** A transfer writes both tables, and whichever one it writes first leaves them disagreeing for a statement — an immediate check could not be satisfied in *any* order. Checking at COMMIT means no order leaves an undesignated superadmin behind, and a transfer that forgets half of itself is still refused.

The last three rules require the transaction to have set `isu.superadmin_transfer`. That is a deliberate-action gate, in the same spirit as the portal's password confirmation, and **not** a boundary against somebody who already has SQL — they could set it too. What it buys is that no ordinary statement, no application bug and no half-remembered maintenance script moves a designation by accident. The boundary against the *application* is a `REVOKE`, which the README spells out; the application never writes that table.

## What the API does

| Route | Before | Now |
| --- | --- | --- |
| `PUT /api/admins/:id/role` | promoted and demoted | **405** `superadmin_set_fixed`, for every caller, target and body |
| `POST /api/admins` with `"role":"superadmin"` | created a superadmin | **409** `superadmin_set_fixed` with `fields.role`, before the password confirmation |
| `POST /api/admins` with `"role":"admin"`, `null` or omitted | created an administrator | unchanged |
| `POST /api/admins` with any other role | 400 `Role must be Administrator or Superadmin.` | **400** `Role must be Administrator.` |
| `PUT /api/admins/:id/status` on one of the four | activated or deactivated | **409** `superadmin_set_fixed`, both directions, before the body is read |
| `PUT /api/admins/:id/permissions` on one of the four | 409 for being a superadmin | **409** `superadmin_set_fixed` |
| `DELETE /api/admins/:id` | already gone | unchanged |

**`/role` is retained as a non-mutating refusal rather than deleted.** A client left over from before this deployment then gets the envelope and a code it can act on — "the server no longer does this" — instead of a bare 405 page it would show as an unexpected error. It reads nothing, takes no lock, asks for no password and looks no target up: a 404 for a missing id would imply that a real one would have worked.

**Creating a superadmin is refused, not quietly downgraded.** The caller asked for an account with Backup & Recovery and account management; a regular administrator under the same username is a different account from the one it thinks it made.

**Status is refused in both directions** because the four are managed outside the portal, not merely kept switched on. Containment deactivates one through the operator procedure; if the portal could switch it back, the containment would last until whoever took the account noticed the button.

**409 rather than 403 throughout.** A 403 with an unrecognised code reads as "confirm your password" to an older client, and no password helps here.

Listings — plus `POST /api/admins` and `PUT /api/admins/:id` — carry **`isProtected`**:

```json
{"id":"7","username":"registrar","email":"…","status":"Active","role":"superadmin",
 "isProtected":true,"isCurrent":false,"permissions":null}
```

A build that does not know the key reads it as absent and merely offers actions the server refuses. Hiding a control was never the protection. The self-edit response carries it too, so an `admin` object merged into a client's row cannot silently clear the flag.

## What deliberately did not change

- **The last-active-superadmin rule stays.** It and the designation answer for different rows: a designated account is refused whatever it would leave behind, while this one protects a superadmin that is *not* designated — which is what every superadmin row looks like on a deployment that has this build and not yet the schema. Without it, such a deployment could deactivate its way out of having any superadmin at all.
- **The four still edit their own credentials** through `PUT /api/admins/:id` and `PATCH /api/profile`, and still receive reset codes from a colleague. What is fixed is who holds the role; protecting the password would only be a reason to keep a stale one.
- **Nothing is cached.** Role and designation are read from the row on every request, so a transfer or a containment lands on each session's next request. The designated set is locked in the same transaction as the administrator rows, after them and in the order the transfer procedure takes them, so a transfer committing mid-request cannot leave a write deciding from a stale set — and two writers queue rather than deadlock.
- Ordinary administrator management — create, configure, deactivate, rename, reset — is unchanged and covered.

## Three bugs this found

Running the invariants against a **real PostgreSQL** rather than a fake store, which is the only place any of this can be checked:

1. `audit_log.created_at` is `NOT NULL` with its default in the model, not the schema — so the migration's audit insert failed outright. `admin.status` is the same. Both fixed, and the README's transfer and containment SQL spells the columns out.
2. `app/tests/admin_permissions_storage.py`'s PostgreSQL path **had never run**: `:id`, part of a route named in the `permissions` column comment, was read as a bind parameter and the whole script refused. Fixed.
3. In that same path, a hand-assigned id does not advance the sequence `POST /api/admins` relies on, so the next create collided. Fixed.

## Deployment

**Schema first, then the application.** The build reads `public.superadmin_designation` on every administrator listing. The *old* build runs happily against the new schema except that a promotion or demotion fails at COMMIT — a safe failure, and the reason the ordering is this way round. Take a backup, keep it off-host, and verify the four with an authorized read-only check before running anything:

```bash
psql "$DATABASE_URL" \
  -v ON_ERROR_STOP=1 \
  -v super1=<id> -v super2=<id> -v super3=<id> -v super4=<id> \
  -f migrations/20261107_fixed_superadmins.sql
```

`ON_ERROR_STOP=1` is required, not advisory. The migration aborts writing nothing unless all of these hold: four distinct ids, every one an existing **active superadmin**, no superadmin outside the four, and the designation table either empty or already holding exactly these four. It does not choose the accounts, demote an extra superadmin, or create anything — a migration that made any of those decisions silently would be the accident this exists to prevent. Re-running with the same four writes nothing and audits nothing twice.

Rollback, the restricted atomic transfer procedure, and urgent containment (including the case where fewer than four accounts are temporarily active) are documented in [README.md § Fixed superadministrators](README.md#fixed-superadministrators). Release assets follow the [production recipe](deploy/README.md).
