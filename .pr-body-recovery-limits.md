The recovery OTP routes capped guesses **per code**, in **process memory**. Three things were wrong with that, and all three are the same mistake — the limit was not attached to the thing being protected:

- **A resend handed back a full budget.** Five guesses per code and a code a minute is about five guesses a minute, indefinitely, which is not a limit.
- **A restart cleared every counter**, so the way past one was to wait for a deploy — and a second worker ran a second set of budgets alongside the first, which is why the deployment had to stay single-worker.
- **Nothing locked recovery itself.** Each code died on its own and the next one started clean.

## The limits

Two now, both persistent, both over the same **15-minute sliding window**:

| Limit | Value | Past it |
| --- | --- | --- |
| Codes requested | 3 per window | 429 `recovery_restricted`, **nothing mailed** |
| Wrong codes guessed | 5 per window | 15-minute restriction, starting with the 5th guess itself |

Unchanged: **10-minute** code expiry, **60-second** resend cooldown.

## The counts belong to an account, not a code

They are kept against a **subject** — an account when the submitted address belongs to exactly one, so its primary and alternative addresses share a single budget and a single request cap, and the address itself otherwise.

So the five guesses are cumulative **across resends, across both of an account's addresses, and across the password and username flows** (both verify the same inbox, so counting them apart would only double the guesses on offer). Two unrelated addresses keep their own budgets — otherwise guessing at an invented address would be a way to lock somebody else out.

## The restriction

The **5th wrong code is itself answered with the restriction**, not `code_exhausted`. "Request a new one" was advice that led straight back to five more guesses.

While a subject is restricted, **every** route answers 429 `recovery_restricted` with an integer `Retry-After` — including a request for a new code, so it cannot be waited out by mailing yourself codes, and **including a request carrying the correct code**. A restriction the right code could walk through would only ever hold up the people who had lost their code.

When it lifts the whole budget comes back; leaving the failures at the limit would restrict the account again on its next mistake, and the next.

## The two decisions #140 asked to have settled

- **A correct code clears the failures**, for a username recovery as much as a password reset: it proves whoever is asking is reading the inbox, which is the only thing the attempt limit was there to establish. It **does not** clear the request window, which is about how much mail the form may send.
- **The failure count decays** once the window passes with no new failure. Five mistakes *in fifteen minutes*, not five in a lifetime — without that, an address that mistyped four codes last month would be one slip away from being locked out for good. The issue did not specify a decay; a cumulative count with none is a permanent lockout, so this is a deliberate reading, documented in the README and covered by a test.

## Telling the two kinds of 429 apart

Flood 429s now carry `code: "rate_limited"`, so the frontend can distinguish "this client is going too fast" (seconds) from "this account's recovery is closed" (minutes). The 60-second cooldown and the per-IP limits are `rate_limited`; the request cap and the restriction are `recovery_restricted`. `invalid_code` still carries `attemptsRemaining`, now the cumulative figure.

**No frontend change is needed**: every recovery step already surfaces a 429 as a countdown driven by `Retry-After`, which is exactly why the integer requirement matters.

## What is stored

`public.recovery_attempt`, one row per subject, counters only.

**No code and no password hash is ever written there.** The codes stay in memory, so a restart still invalidates outstanding codes and the admin asks for another — losing those costs an attacker nothing, which is why they are the part that may be lost. What survives a restart is the part an attacker *benefits* from losing.

An address with **no account** is stored as `email:` plus an HMAC keyed with `SECRET_KEY`, never as the address: the table would otherwise become a list of every address anybody has typed into Forgot Password — addresses that by definition belong to people with no account here — and an email address is guessable enough that an unkeyed digest is a dictionary away from the address.

Rows untouched for longer than both windows remember nothing and are swept, which also keeps a flood of invented addresses from growing the table.

Within one process a lock serializes the read-decide-write; across processes `SELECT … FOR UPDATE` on the subject's row does the same, so several workers count once per guess rather than once per worker.
